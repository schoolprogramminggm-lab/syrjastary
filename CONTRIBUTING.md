# Как работать над проектом

Документ для участников разработки. Прочитать один раз перед началом,
дальше возвращаться по мере надобности.

Правила кода — в `CLAUDE.md`. Здесь про процесс.

---

## Подготовка окружения

Выполняется один раз.

**Что нужно установить:**

- Node.js 20 или новее — проверить `node -v`
- Git — проверить `git --version`
- Expo Go на телефон (App Store / Google Play)
- Редактор кода, рекомендуется VS Code

**Запуск проекта:**

```bash
git clone https://github.com/schoolprogramminggm-lab/syrjastary.git
cd syrjastary
npm install
npx expo start
```

В терминале появится QR-код. Android — сканировать через Expo Go,
iOS — обычной камерой. Телефон и компьютер в одной сети Wi-Fi.

Не подключается — попробовать `npx expo start --tunnel`.
Стили не применяются — сбросить кеш: `npx expo start -c`.

**Перед первой задачей:**

- Прочитать `CLAUDE.md` — правила кода
- Открыть макеты из `design_handoff_jastar_mobile/` в браузере
- Убедиться, что приложение запускается на телефоне

## Рабочий цикл

Одна задача — одна ветка — один pull request.

### 1. Взять задачу

Задачи лежат во вкладке **Issues**. Взять ту, что назначена на вас.
Перевести на доске в колонку **In Progress**.

### 2. Создать ветку

```bash
git checkout main
git pull
git checkout -b feature/название-задачи
```

`git pull` обязателен — иначе будете работать на устаревшем коде
и получите конфликты при мерже.

Именование веток:

```
feature/screen-menu     новая функциональность
fix/tab-bar-padding     исправление
```

### 3. Работать

Коммитить по ходу, не одним большим коммитом в конце:

```bash
git add .
git commit -m "feat: сетка меню в две колонки"
```

Формат сообщений:

```
feat: что добавлено
fix: что исправлено
refactor: что переработано без изменения поведения
style: правки вёрстки и отступов
```

### 4. Проверить перед PR

- `npx tsc --noEmit` — без ошибок
- `npx expo start` — приложение запускается, экран открывается на телефоне
- Экран сверён с макетом визуально
- В коде нет hex-цветов, нет `any`, нет `StyleSheet.create`
- Отмечены все чекбоксы в issue

### 5. Отправить

```bash
git push -u origin feature/название-задачи
```

На GitHub появится предложение создать pull request. Создать.

**В описании PR написать два-три предложения:** что сделано и почему
выбрано именно такое решение. Если были нестандартные ходы — объяснить их.

Добавить строку `Closes #N`, где N — номер issue. Тогда при мерже
задача закроется автоматически.

### 6. Дождаться ревью

PR проверяет руководитель проекта. Могут быть замечания — это нормальная
часть процесса, а не оценка работы. Исправления делаются в той же ветке:
новый коммит и push, PR обновится сам.

**Свой PR не мержить.** Merge делает руководитель.

## Про Claude Code и AI-ассистентов

Использовать можно и нужно — но с понимаем границы.

**Разумно поручать:** раскладку компонентов по файлам, типизацию,
перенос вёрстки из макета в JSX, рутинные правки по всему проекту.

**Делать самому:** отладку, когда что-то не отображается; подгонку
отступов по макету; разбор ошибок TypeScript; git-операции.
Здесь и формируется навык.

**Главное правило: не коммитить код, который не можешь объяснить.**

Если ассистент написал компонент, а вы не понимаете, зачем там конкретная
конструкция — разберитесь до коммита. Описание PR как раз это и проверяет:
если не получается написать, что сделано и почему, значит разбираться рано.

**Как ставить задачу ассистенту:**

- что сделать, по пунктам
- где источник (файл макета, секция)
- куда положить результат (конкретные пути)
- чем проверить
- что не трогать

В конце добавлять:

```
Проверка: npx tsc --noEmit чисто, npx expo start поднимается.
Если что-то конфликтует по версиям — не обходи проблему,
останови работу и покажи ошибку.
Лишних пакетов не ставь. CLAUDE.md не редактируй.
```

Без последнего он начнёт решать проблемы самостоятельно: подставит
замену, понизит версию пакета — и разбираться придётся потом.

**Не соглашаться,** если ассистент предлагает изменить структуру папок,
заменить библиотеку или обойти правило из `CLAUDE.md`. Написать в чат.

## Безопасность

Репозиторий **публичный** — всё, что попадёт в коммит, увидит любой.

- `.env` не коммитить никогда. Он в `.gitignore`, эту строку не трогать
- Ключи, пароли, токены не вставлять в код, даже временно
- Если ключ случайно ушёл в коммит — **не удалять его новым коммитом**,
  а сразу сообщить руководителю. Ключ придётся перевыпускать: из истории
  публичного репозитория его уже забрали боты

## Когда писать в чат

- Задача закончена, PR создан
- Что-то не получается — **с текстом ошибки**, не пересказом
- Ассистент предлагает решение, в котором не уверены
- Результат не совпадает с макетом и непонятно, как правильно

Полчаса застревания на одном месте — уже повод написать.
Копить вопросы до конца дня не нужно.

## Частые ошибки

| Симптом | Причина |
|---|---|
| Стили не применяются | кеш Metro — `npx expo start -c` |
| Конфликты при мерже | забыли `git pull` перед созданием ветки |
| Push отклонён | пытаетесь пушить в `main`, нужна своя ветка |
| Expo Go не подключается | разные сети Wi-Fi или фаервол — `--tunnel` |
| `Module not found` после pull | появились новые зависимости — `npm install` |
